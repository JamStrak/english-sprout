## 每次发布

1. 在正式工程核实版本、工作树和提交范围；完成产品要求的测试，公开构建 `npm run build`，确认 `dist/xiaoya/version.json` 的版本、构建号和 `public` 渠道，确保不包含内测 GM、日志、本地配置或儿童数据。核心改动按项目约定验证新旧产品和相关浏览器回归。将核对过的产品改动及交接提交 Git，并保留可回退点。
2. 先比较远端 `main` 与开发分支，核对旧产品差异并安全整合；不得强推或覆盖旧站。发布到 `main` 后检查 GitHub Actions 和 Pages 是否成功，实测 `/xiaoya/` 的版本及关键资源，同时回归旧产品入口。GitHub 的构建号可能因构建环境不同而变化，以实际线上版本和对应资源为准。
3. 给用户生成可复制的 WorkBuddy 提示词，写清本次 GitHub 提交、版本、GitHub 新版地址、源码位置、公开构建要求、现有国内站及禁止上传的内容。由用户自行查看额度、粘贴任务和操作 WorkBuddy；Codex 不操作 WorkBuddy。
4. GitHub 上核对实际版本、关键文件及页面可用性；国内站由用户交给 WorkBuddy 验证并报告版本、资源及部署结果。记录提交、构建号、发布结果和未验证项。未获得国内站验证结果时，不声称国内站已更新。
