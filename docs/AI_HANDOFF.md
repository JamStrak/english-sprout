适用：小芽英语·自由花园版 v0.20.0（`xiaoya/`）；建立于 2026-10-19，更新于 2026-10-21。内测构建 `388ea80d6881`、公开构建 `ea9dc9eea89e`，交付提交与功能基线见 [当前状态](../PROJECT_CONTEXT.md)。本文件不依赖 Codex、原聊天记录或某一家 AI 服务。需要的是能读写文件、使用 Git 和执行本机命令的工具；只有聊天能力的工具可先产出方案和补丁，由具备执行能力的工具验证落地。

若交回原 AI，也使用同样入口，加上任务分支、起点提交和交付提交即可，不必重讲全部历史。必须附本次用户目标；单靠一个提交号无法说明什么应当保留。

## 接手的前五分钟

在用户指定的工程中执行只读检查：

```powershell
git rev-parse --show-toplevel
git branch --show-current
git rev-parse HEAD
git status --short
git worktree list
```

1. 对照 [PROJECT_CONTEXT](../PROJECT_CONTEXT.md)，确认是当前小芽英语，而非旧主目录、旧包或仅有 `dist` 的运行包。本机绝对路径只是定位线索，换设备后以实际 checkout 为准。
2. 读 `AGENTS.md` 和当前状态，了解本次用户目标。再按 [资料索引](INDEX.md) 只读相关模块；无需全量读取历史、全部聊天或用户私人资料。
3. 有未提交改动时先核对归属。不要 `reset --hard`、`clean`、覆盖存档或把无关文件一起提交；历史未完成项也不能自动变成本次任务。
4. 明确本次是产品实现、资源制作、设计讨论还是只读审查。已有授权内的工作持续执行，只有缺失信息实质改变结果或超出授权时才问。
5. 记录实际起点 SHA、允许修改范围和验收标准。简单修复可记在现有实施记录；多方并行或暂时转交才需要单独任务交接单。

事实冲突时核对当前用户要求、代码与实测结果，并把偏差写清。历史文档中的“现在”“下一步”“通过”只适用于当时版本；不能用旧验收替代当前验证。

本机位置约定（2026-10-20）：当前新产品工程在 `E:\AI新项目\其他实验\儿童英语练习\小芽英语`；后续辅助工作树、生成资源、构建包与测试产物也放在用户指定的 E 盘项目根目录内，不使用 C 盘的工具默认工作树位置。子工作树与父目录旧产品共享父目录 `.git`，父仓库本地 `.git/info/exclude` 已排除 `/小芽英语/`。在父目录运行 Git 不等于在新产品分支工作，先切换到实际子目录再操作。换设备仍按下文完整仓库或 bundle 方法迁移，不能只复制 `.git` 指针。

## 一次只交出一个清楚的任务包

使用 [任务交接模板](templates/AI_TASK_HANDOFF.md)。最少包括目标、输入目录和基线、文件归属、不得破坏的行为、验收方法、交付分支/提交及整合负责人。开发者可以提出必要调整，但不能把创意建议写成已批准设计。

- **轮流接手**：前一位完成提交，说明仍未提交的文件及原因；下一位检查状态后继续。不要要求每次换 AI 都重新建产品或换技术栈。
- **并行辅助**：一项功能一个分支/工作树，写明文件归属；没有交叉的文档/素材任务也可共享目录，但仍需指定整合者。多人同时修改 `experience.js`、`runtime.js`、课程表、构建脚本或当前交接入口时，优先隔离，不能靠“最后写入”合并。
- **同机新分支**：先核对已有分支和 worktree；从约定的完整起点 SHA 创建，不默认从旧 main 开始。默认名称 `codex/任务短名`，不要重复使用仍由别人工作的目录。
- **辅助任务返回**：说明修改哪些文件、哪些没改、验证到哪一步。整合者复核差异后再合入，不把一句“已经好了”当验收证据。

分支示例是模板，替换路径和 SHA 后使用；目标目录必须是新的目录：

```powershell
git worktree add -b codex/feature-name 'D:\work\xiaoya-feature' <完整起点SHA>
```

## 运行、测试与审核

普通试用及重启电脑后双击当前工程的 `启动小芽英语.vbs`，进入自由花园版；本机父目录也有 `启动小芽英语最新版.vbs` 转交入口。启动器按本地构建选择 `start-<build>.html`，绕过已安装旧服务工作线程的首页缓存，保留相同 origin 和存档。新版 SW 安装后，旧 `start-<hash>.html` 在线也取当前入口，离线取该 SW 已校验入口。不能只凭 URL 或 VBS 日期判断版本，应核对页面标题/页头、GM 实际版本与 `dist/xiaoya/version.json`。开发命令、环境变量和各项测试入口见 [技术地图](XIAOYA_ENGINEERING.md)。不要因根 `package.json` 的旧版本号、`npm run preview` 或旧文档误启旧应用。

- 声音包 848 段、图片包 223 张（195 故事＋28 纸艺），后台完整校验后才激活新 SW，未浏览的正式图片也包含在内。家长页可查看插画包进度/重试；GM 审图库 228 项另含 5 个图标，不能当成故事数量。浏览器清除站点数据后仍需服务重新取得资源，不承诺缓存永久存在。
- `npm run build:dev` 生成内测版；`npm run build` 生成公开版，两者共用 `dist`。切换构建会影响正在试用的本地包，应记录最后保留的渠道和版本。
- 正式版本交付运行 `npm test`、对应构建及与改动相关的检查；界面/媒体改动加新产品浏览器检查和旧产品回归，启动器变更加 Python 测试。纯文档更改核对事实、链接和差异即可。
- GM 可审核素材、指定句子和无需录音的流程。它不能验收真实语音识别、儿童发音或学习效果。模拟进度只在页面内存，不拿它覆盖正式儿童记录。
- 自动化测试使用独立浏览器上下文与模拟数据；不要向用户正在试用的浏览器注入样例存档、清 localStorage 或循环刷奖励。
- 原始 `test-results/` 被 Git 忽略。提交中保留精简可移植的验证摘要，列命令、实际版本/构建渠道、结果、跳过原因、证据位置及范围。若日志只在本机，要明确标注，不假设接手者一定拿得到。
- 不把“定向补测通过”改写成“全套已重跑”，不把屏幕模拟 390px 写成真机验收。遇到失败先保存原因和实际结论，再决定修复与重测范围。

## 换工具、换设备与离线交接

同一电脑换 AI 工具：让新工具打开实际工程即可，项目无需重新安装某个 AI 平台。工具专用入口、浏览器路径或个人技能目录不是项目依赖。Windows 普通用户启动器、本机生产脚本中的路径需按技术地图核对；其他系统可用 Node/Python 命令入口。

换设备应传递**完整 Git 仓库中的目标分支和已跟踪运行资产**。当前目录是 Git worktree，它的 `.git` 是指向主仓库的文件，直接复制这个文件夹不能得到自包含 Git 仓库。仅复制 `dist` 可用于部署静态站点，但不足以继续开发。不要把凭据、`.runtime`、真实学习导出、个人制作环境或全部聊天打进交接包。

已有可信远端且目标提交已存在时可正常 clone/fetch；未检查前不要假设本机分支已经推送。没有远端或需要离线交接，可在**提交核对过的改动后**制作 Git bundle。下面路径为示例，应使用自己选定的新文件与目录：

```powershell
# 发送端，在正确工程；目标文件放仓库外，先确认不存在
git bundle create 'D:\handoff\xiaoya.bundle' codex/xiaoya-garden-ab
git bundle verify 'D:\handoff\xiaoya.bundle'

# 接收端，目标目录应不存在
git clone -b codex/xiaoya-garden-ab 'D:\handoff\xiaoya.bundle' 'D:\work\xiaoya'
```

bundle 含该分支可达的 Git 历史与已跟踪文件，不含未提交改动、忽略文件和用户浏览器存档；仍应核查适合交接的范围。以上仅提供方法，本次文档整理不自动打包、外发或推送。接收后核对 HEAD，安装/定位 Node 与 Python，按技术地图构建；运行图片、配音、识别模型及许可文件已经在仓库，不依赖实验室原图才能运行。

浏览器测试需另装或定位 Playwright，按脚本设置 `PLAYWRIGHT_MODULE`；某台机器可用的默认绝对路径不代表其他工具或设备也有。配音再生产、修图的制作环境另见内容流水线；只运行现成 app 不需要这些生产工具。

**学习数据与工程分开**：新版目前支持导出，尚无导入或跨设备自动同步。浏览器存档按 origin 隔离，换域名/端口/浏览器可能看不到原记录。保存工程、复制 bundle 或下载 GM 模拟导出都不能迁移孩子进度。未经明确迁移需求，不承诺已经备份或恢复真实记录。

## 做完后怎样交回

1. 自查差异并运行适用检查，更新行为变化对应的现行文档。历史记录只追加或标明被替代，不抹掉原失败范围和版本。
2. 明确哪些文件属于本次工作。用显式路径 `git add`，不要默认 `git add .`；提交后给出完整 SHA、分支、起点 SHA、验证及实际限制。不要为求工作区干净而提交无关文件。
3. 当前状态只维护当前结论与导航；详细过程写入 [实施记录](XIAOYA_IMPLEMENTATION.md)。重要接口、存档、资源或启动变化同步技术/内容/使用文档；纯审查不强造版本发布。
4. 若异地交回，发送分支 bundle，或在确认接收者有起点时生成 `git format-patch --binary <起点SHA>..HEAD --output-directory <新输出目录>`。同时附交接单；只发截图或散文件会丢失变更依据。
5. 接回者先比较当前 HEAD 与任务起点、检查未提交改动，再审查具体提交。选择正常合并或挑选提交，解决语义冲突并验证；不要把整个旧目录覆盖到新版本。遇到冲突保留双方改动依据，特别核对稳定 ID、缓存与奖励账本。
6. 合并后的验证属于新的集成版本，记录实际提交和构建指纹。不得把辅助分支的通过结果直接称为集成版通过。推送 main 会触发既有 Pages 发布，未获部署授权不要推送。

交回摘要使用以下顺序：**做成了什么 → 基线/交付提交 → 实际验证 → 未完成或未验收 → 下一位明确要做什么**。没有遗留开发任务就写“无”，不要为了交接制造待办。用户之后再指定目标时，由新任务覆盖旧候选方向。
